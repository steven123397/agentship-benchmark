# Baseline 候选测试与归档规则

## 适用范围

本文件适用于 `baselines/` 下的 baseline 准备材料、候选运行归档和评审资料。产品源码仍由对应独立产品仓库的规则管理。

每个版本目录中的以下文件分别是单一事实来源：

- `development-brief.md`：发给候选 Agent 的固定开发委托。
- `evaluation-and-scoring.md`：评测对象、评分规则、风险标记和验收边界。
- `review-prompts.md`：冻结候选的评审索引，以及各审查者的通用委托。
- `runs/<candidate-id>/`：单个候选的事实、证据和评分，不承担通用流程说明。

## 公平与隔离

- 所有候选使用同一冻结 baseline、开发委托、数据集、评分规范和环境边界；不要因 Agent、模型或 Harness 名称改变要求和评分尺度。
- 不限制候选 Agent 自身可用的原生工具和 skills，但必须如实记录可确认的外部条件与实际使用情况。
- 候选开发期间，不向候选提供其他候选的源码、分支、工作树、报告、分数、问题或运行证据。
- 协调方可以读取既有归档来维护统一流程，但不得把其他候选的结论迁移为当前候选的证据。

## 新测试流程

### 1. 只读预检

在创建任何资源前，确认：

1. 用户指定的候选 ID、Agent、模型或 Harness，以及产品仓库和 baseline 版本。
2. baseline tag 与完整 commit SHA，目标分支和工作树是否已存在。
3. AgentShip 与产品仓库的当前分支、未提交改动和已有 worktree。
4. 该版本的开发委托、评分规范、固定数据集和现有候选命名方式。

发现身份冲突、目标已存在或可能覆盖现有改动时停止，不猜测、不清理。

### 2. 最小启动

用户明确要求“新增”或“开启”一个候选测试时，只准备开始测试所必需的资源：

- 从冻结 baseline 创建用户指定或确认的候选分支与独立 worktree。
- 校验 worktree 的 `HEAD`、分支和洁净状态；运行低成本的固定输入校验。
- 仅在用户要求时启动指定的 Agent 或 Harness 入口。
- 默认不在 AgentShip 创建 `runs/<candidate-id>/` 或任何占位文件，候选完成后再统一归档。
- 只有用户明确要求持久化进行中状态时，才创建最小 `metadata.json`，且只登记候选身份、baseline、分支、工作树和当前阶段；不得顺带创建评审、评分、复现、效率或 skill 占位文件。

启动阶段是否需要额外环境检查、状态记录或 Harness 操作，由协调方按当前任务目标和证据需要自主判断；不得提前创建整套占位归档、修改评分规范、写入未发生的验证结果，或替候选跨越尚未完成的开发阶段。任何 `git commit` 仍遵守根 `AGENTS.md` 的单独审批要求。

### 3. 开发期间

- 候选由用户与对应 Agent 或 Harness 推进；协调方在当前测试目标内自主处理环境、状态核对、记录和阶段衔接，不为普通操作逐项请求批准。
- 不把标准工作树创建、Harness 启动、页面可访问等准备动作写成候选完成证据；Harness 页面 HTTP 200 只表示工具入口可用，不表示产品可运行。
- 不为了让记录显得完整而估算时间、token、skill、完成状态、测试结果或评分。
- 非标准人工介入先保留可核对事实，在候选完成归档时写入；同一事实只写入职责对应的一个文件，其他文件最多引用它。

### 4. 完成与冻结

只有在用户报告候选完成并要求继续处理后，才进入冻结阶段：

1. 核对候选工作树、分支、完整结果 SHA、Git 状态和 Agent 完成摘要。
2. 未经明确的提交批准，不替候选创建 commit；推送已有提交不需要单独批准。没有稳定结果 SHA 时不得标记为冻结。
3. 按评分规范独立复现固定数据集、测试入口、启动与就绪、允许与拒绝路径、浏览器主链和必要的安全探针。
4. 将用户或 Agent 报告与协调方独立验证分开记录；未执行或失败的项目明确标为未验证或失败。
5. 仅清理本阶段明确创建且可准确归属的运行资源；删除 worktree、分支、卷或远端引用前精确核对目标，不需要重复请求批准。
6. 冻结完成条件是：结果 SHA 明确、候选身份一致、工作树状态已记录、复现范围已记录、未验证项可见。

### 5. 独立评审与汇总

- 只有 `metadata.json` 已标记冻结且 `candidate.resultCommit` 为完整 SHA 时，才可启动首轮评审。
- 每次评审开始、首次运行前、写报告前和结束时，都核对候选路径、分支、`HEAD` 与唯一报告文件；任一身份不一致立即停止。
- Codex 与 Grok 互盲评审，只写各自的报告，不读取对方报告、汇总或评分卡。
- 两份报告都完成后再汇总技术分和风险标记；人工文档分与视觉分由用户给出。不得按候选名称采用不同评分标准。
- 评审发现的问题只属于被审查的冻结候选，不能转移给其他候选，也不能用后续修复提交覆盖首轮结果。

## 运行归档职责

候选完成后按实际证据创建或补全所需文件，不要求在启动时生成空壳。文件职责如下：

- `metadata.json`：候选身份、baseline、结果 SHA、阶段、冻结状态、远端状态、可复现运行资源索引和结构化评分结果。
- `reproduction.md`：协调方实际执行的命令、环境、结果、失败和未验证项；不重复工具启动叙事或评分结论。
- `intervention-log.md`：开发过程中改变候选路径或体验的非标准人工介入；标准工作树与 Harness 启动通常不记为介入。
- `efficiency.json`：有来源的时间、token、成本和开发体验事实；不能观测时使用 `null`，不估算精确值。
- `skills.json`：可确认的外部 skill 和 Agent 内建 skill 使用情况；未报告的不推断。
- `codex-review.md`、`grok-review.md`：各审查者的原始首轮报告。
- `review-summary.md`：两份首轮报告的汇总、分歧、人工分和风险标记。
- `scorecard.md`：最终展示分、风险与独立的过程调整，不保存详细复现日志。
- `screenshots/`：评分或复现实际使用的截图；没有截图时不为形式完整而创建占位内容。

候选专用工具或 Harness 的版本、入口和配置，只有在影响公平性、可复现性、耗时或结果解释时才记录，并放入一个最合适的事实文件。不要把相同的启动命令、端口、健康检查和配置归属重复写入 `metadata.json`、`reproduction.md`、`intervention-log.md` 与 `efficiency.json`。

## 变更检查

每次修改归档后至少检查：

1. JSON 可解析，状态、SHA、分数和风险字段彼此一致。
2. 新增候选没有继承其他候选的分数、证据、路径或资源名。
3. `git diff --check` 通过，差异只覆盖当前授权范围。
4. 当前任务未获提交授权时不得创建 commit；可以暂存，但必须准确汇报暂存状态。
