# DecisionHarbor v0.1.0 评审与评分规范

## 范围与目标

本文定义 DecisionHarbor `baseline-v0.1.0` 首轮开发任务的运行、复现、评审和评分规则。它评价完整的 AI 开发 Agent 系统在同一产品起点、同一开发委托和同一运行环境中，能否交付安全、可运行、可维护的产品基座。

本轮质量分为 100 分。其中前 90 分技术项由 Codex CLI 与 Grok Build 独立评分后取算术平均；产品文档与交付清晰度 5 分及自发前端视觉质量 5 分由人工最终裁定。P0/P1/P2 风险、时间、token、成本与人工介入均另行记录，不进入质量分。产品仓库不得保存本文、评分规则、隐藏用例或结果比较材料。

当前计划记录的系统标签如下；标签只用于归档，不影响评分：

- Codex CLI：`gpt-5.6-sol-xhigh`
- Grok Build：`grok-4.5-high`
- Grok Build：`grok-4.6-high`
- Kimi Code：`kimi-k3-thinking`
- ZCode：`glm-5.2-high`
- Qoder：`Qwen3.8-Max-Preview-thinking`
- Claude Code：`claude-fable-5`

## 固定输入与不变量

每次运行必须记录并冻结：

- DecisionHarbor 产品仓库远端、`baseline-v0.1.0` tag 和精确 commit；
- 开发委托版本、固定销售数据集版本和数据契约哈希；
- 宿主机、Docker、Node.js、Python、PostgreSQL 和浏览器版本；
- 分支名、结果 commit、开始/结束时间、token、成本和人工介入记录。
- 共用外部 skill 基线的目录、清单与 `SKILL.md` 哈希，以及本次实际使用的外部 skill；Agent 内建 skill 单独如实记录，不猜测或补齐。

每个系统从相同 baseline 创建独立分支和 worktree。产品分支统一命名为 `<baseline-tag>/<normalized-agent-model>`，以便在远端按评测版本聚合；运行档案目录继续使用稳定的候选标识，不随工作树路径变化。运行中不得读取、比较或使用其他结果 worktree、分支、提交、运行记录、评审材料或已完成答案。评审时不得因名称、模型、成本、耗时或既往印象改变任何评分子项。

Agent 的原生工具、搜索、浏览和工作方式属于被评系统的一部分，不作限制。允许正常访问依赖仓库、镜像仓库、操作系统包源、官方技术文档与正常搜索；不得为某一系统额外提供私有依赖、镜像缓存、账号或人工检索结果。

## 关键决策与取舍

| 决策 | 结论 | 理由与放弃的方案 |
| --- | --- | --- |
| 审查者角色 | Codex CLI 与 Grok Build 共同进行首轮独立复核；两者不是满分参照或规则校准特权。 | 相对单一系统给分会把特定实现风格误当产品标准；两者使用同一绝对量表，独立证据互为制衡。 |
| 工具能力 | 保留每个 Agent 的原生工具与搜索能力。 | 本项目评价完整 Agent 系统；强行抹平工具能力会改变被评对象。 |
| 技能环境 | 所有候选使用同一份共用外部 skill 清单；内建 skill 不做抹平，但必须如实记录。 | 外部技能差异会形成不可追溯的额外输入；内建能力属于 Agent 系统本身，不能假定各系统相同。 |
| 质量与效率 | 质量 100 分独立，效率单独记录。 | 计费、token 与原生工具差异过大，不应掩盖产品交付质量。 |
| 复现与评审 | 提示词一、二可受控并行；实现、运行时验证和复现串行，统一环境。Codex 与 Grok 首轮审查均只读，且在汇总前不得读取对方报告。 | 文档阶段不占用 Compose 运行资源；实现和复现阶段的并发资源竞争会污染证据，评审修改结果或互相锚定会破坏可追溯性。 |
| 验收材料 | 公开契约配合同一份非公开边界 harness。 | 只公开用例会弱化安全边界，完全隐藏又无法让开发目标可理解。 |

## 首轮评分合成

Codex CLI 与 Grok Build 分别对以下 5 个技术维度独立评分，共 `90` 分：功能与外部契约 `25` 分、SQL 治理与数据正确性 `20` 分、可运行性与可靠性 `20` 分、测试与验证证据 `15` 分、代码质量与可维护性 `10` 分。两者在首轮报告冻结前不得访问、引用、转述或依据对方的报告、分数、问题清单或截图。

设 Codex 技术分为 `C`，Grok 技术分为 `G`，人工文档分为 `D`，人工视觉分为 `V`，则：

```text
技术平均分 = (C + G) / 2
质量分 = 技术平均分 + D + V
```

其中 `C`、`G` 的取值范围均为 `0–90`，`D`、`V` 的取值范围均为 `0–5`。质量分可以保留 `0.5` 分。两位审查者均须为技术评分和文档建议引用具体代码或运行证据；人工只在汇总阶段给出 `D` 与 `V`，不向任何一方透露另一份首轮报告。

P0/P1/P2 不是可平均的分项，也不对质量分施加封顶或额外数值扣减。触发风险标记的事实必须先在相关技术子项中体现；风险标记随后以独立字段展示，说明候选是否适合安全上线、基座交付或完整闭环。候选质量比较只按质量分排序，不因风险标记改变质量排名。时间、token、成本和人工开发者体验与风险标记一样单列展示；其中已由用户明确指定的开发者体验调整不得改写质量分，但可另给出“体验调整后展示分”。

## 质量分与评分档位

质量分按下表计算。除人工裁定项外，每个子项使用三档：未通过为 `0`，部分通过为该子项的 `50%`，完全通过为满分。非公开 harness、命令输出、HTTP 响应、浏览器证据和代码审查是判断依据；Agent 自述不构成通过证据。总分可以保留 `0.5` 分。

| 维度 | 分值 | 子项 |
| --- | ---: | --- |
| 功能与外部契约 | 25 | 查询运行 API 生命周期 8；允许查询结果正确性 7；拒绝与执行失败语义 5；最小查询工作台 5 |
| SQL 治理与数据正确性 | 20 | AST 只读语义与单语句约束 6；授权对象与 schema 范围 4；数据库身份与双库隔离 4；执行资源限制 3；固定数据契约与业务口径 3 |
| 可运行性与可靠性 | 20 | 干净环境启动与就绪 6；迁移与固定数据初始化 6；并行实例隔离 5；重启与故障可见性 3 |
| 测试与验证证据 | 15 | 统一测试入口与可靠断言 3；SQL 策略单元测试 5；双数据库集成测试 4；浏览器主链测试 3 |
| 代码质量与可维护性 | 10 | 模块边界与职责分离 3；配置、错误处理与资源清理 3；类型、命名、重复控制与可测试性 2；依赖、变更范围与维护负担 2 |
| 产品文档与交付清晰度 | 5 | 治理、索引与阅读入口 1；设计完整性与可追溯性 2；计划、运行/测试说明与实现一致性 2 |
| 自发前端视觉质量 | 5 | 由人工在固定观察场景下综合评分 |

### 功能与外部契约

- 查询运行 API 生命周期：`POST /api/v1/query-runs` 创建查询记录，`GET /api/v1/query-runs/{id}` 可读取状态与审计事实。
- 允许查询结果正确性：针对固定数据集的筛选、聚合、连接或 CTE 查询返回正确列、行、行数和耗时。
- 拒绝与执行失败语义：非法输入具有稳定状态、错误码、可读说明和记录标识，不伪装为成功。
- 最小查询工作台：可输入与提交 SQL，显示执行中状态、成功结果、拒绝或失败信息。

### SQL 治理与数据正确性

- AST 只读语义与单语句约束：允许 `SELECT` 与 `WITH ... SELECT`；拒绝多语句、DML、DDL、数据修改型 CTE 与 `SELECT INTO`。策略必须基于 AST，不能退化为字符串黑名单。
- 授权对象与 schema 范围：只允许访问 `analytics` 中的五张业务表，拒绝系统目录、未授权对象与绕过限定的引用。
- 数据库身份与双库隔离：用户 SQL 必须由独立分析只读身份执行，不能读取或写入 `platform`。
- 执行资源限制：语句超时和结果行数上限真实生效。
- 固定数据契约与业务口径：五表、关联、数据、订单状态、销售额、成本和毛利计算符合契约。

### 可运行性与可靠性

- 干净环境启动与就绪：一条受支持命令构建并启动 Web、API 和 PostgreSQL；`/health` 与数据库、迁移就绪后的 `/ready` 成立。
- 迁移与固定数据初始化：两个逻辑数据库、身份、迁移和固定数据正确建立；重复执行不破坏或重复数据。
- 并行实例隔离：Compose 项目名和宿主端口可配置，不使用固定容器名、全局网络、全局卷或共享绑定目录；两个实例可同时存在。
- 重启与故障可见性：重启后服务可恢复；依赖未就绪时 `/ready` 准确失败。

### 测试与验证证据

- 统一测试入口与可靠断言：存在可执行的统一测试命令；失败产生非零退出，不依赖人工查看日志判断结果。
- SQL 策略单元测试：覆盖允许查询、DML/DDL、多语句、修改型 CTE、未授权对象和边界语法。
- 双数据库集成测试：证明迁移、seed、平台与分析库隔离、只读身份和实际查询执行。
- 浏览器主链测试：覆盖提交 SQL、执行状态、成功结果及至少一种拒绝或失败展示。

### 代码、文档与视觉

代码质量由独立的 Codex 与 Grok 审查按表中 4 个子项分别评分，并计入各自的 90 分技术总分。两者都必须引用具体代码或运行证据；个人风格不是扣分理由，只有会提高缺陷、扩展成本、运行风险或违反既有设计的具体问题才能扣分。汇总时，人工只能基于可核验的证据纠正明显事实或计算错误，并记录理由，不以个人偏好替代两者的独立评分。

文档项由 Codex 与 Grok 按表中 3 个子项分别给出结构化建议分和引用证据。人工根据实际内容表达与交付观感独立给出最终 `0–5` 分；若与任一建议不同，记录简短理由。只评价产品内生文档，不要求面向评审的额外报告。

视觉项由人工独立给出 `0–5` 整数分。在同一桌面视口观察空态、输入 SQL、执行中、成功结果和拒绝或失败状态，综合评价信息层级、布局与密度、状态反馈、表格可读性、视觉一致性和细节完成度。它不奖励营销页、插画或超出需求的复杂交互，也不因功能分数低而额外扣分。

## 关键风险标记

风险标记不改变质量分或质量排名。它们用于说明候选的上线资格和风险性质，并与效率、token、成本和人工开发者体验一起单独展示。一个候选可同时具有多个标记。

| 级别 | 条件 | 展示含义 |
| --- | --- | --- |
| P0 安全失败 | 用户 SQL 能写入数据、访问系统或未授权对象、通过平台写入身份执行，或绕过 AST 治理 | 首轮不具备安全上线资格。 |
| P1 基座失败 | 无法在规定环境启动，或 `/health`、`/ready`、迁移、固定数据 seed 中任一核心链路不成立 | 首轮不具备可交付基座资格。 |
| P2 核心闭环缺失 | 不能同时证明一条允许查询和一条拒绝查询，或最小查询工作台不可用 | 首轮核心闭环未完成。 |

任一首轮报告给出可复核证据，且汇总时确认命中条件，即记录对应风险标记。风险的根因必须同时反映在功能、SQL 治理、可运行性、测试或代码质量等相关技术子项中；不得把标记本身再作为第六个扣分维度。

## 验收证据与评审流程

验收分为公开层和非公开层。公开层是产品背景已承诺的 API、数据契约、启动和测试要求。非公开层是同一份版本化 harness，覆盖 SQL 绕过、schema 或系统对象访问、真实只读权限、超时与行数限制、重复 seed、并行 Compose 和 API 边界。非公开用例只验证既定评分子项，不引入新需求；它只存在于 AgentShip 或外部评测环境，不进入产品仓库。

每个结果按以下顺序评审：

1. 冻结首轮结果 commit、提示词版本、环境版本和运行元数据。
2. 在冻结候选工作树或独立 review worktree 中从头复现启动、迁移、seed、测试、健康检查、允许/拒绝 SQL 和浏览器主链，并保存命令和输出。直接使用候选工作树时，开始与结束都必须记录 `HEAD`、`git status --short --branch` 和 `git diff --check`；发现非忽略改动时不得自行清理或继续评分。
3. 从 AgentShip 当前工作区分别启动只读 Codex 与 Grok 首轮审查。每一方可以查看候选结果、运行复现命令、检查代码与截图，但不得修改产品结果，也不得读取对方的首轮报告、分数、问题清单、截图或汇总文件。每一方输出自己的 90 分技术评分、文档建议分、运行问题清单及证据。
4. 两份首轮报告均冻结后，人工给出文档与视觉最终分；在 `review-summary.md` 中计算技术平均分与质量分，并独立确认 P0/P1/P2 风险标记。若人工纠正了事实或计算错误，必须记录证据和理由。
5. 在 `scorecard.md` 记录各项得分、部分通过理由、风险标记、质量分及任何已预先记录的过程调整，形成首轮结果展示。

缺少必要环境导致无法执行的检查标为“未验证”，不得按通过计分。若有证据证明是评测环境故障，可在环境恢复后以同等条件复跑。

## 首轮后的反馈修复

首轮评分完成后，用户可以将首轮问题反馈给对应 Agent，要求其在原候选分支上形成第二次提交。首轮的 `resultCommit`、首轮报告、评分和风险标记此时永久保留，不因后续修复而重算、覆盖或替换。

每次反馈修复必须在 `remediation/` 下记录：反馈的问题与来源、首轮 commit、修复 commit、Agent 自述的验证、以及 Codex 对每个问题的“已修复 / 部分修复 / 未修复 / 无法验证”结论和证据。该 Codex 跟进审查只核对反馈问题及其修复结果，不重新给分、不改变首轮风险标记，也不生成第二份正式评分卡。

## 规则冻结

首次评审完成后，用户确认进行一次统一的评分展示修订：保留既有 `90 + 5 + 5` 质量维度、首轮证据和 P0/P1/P2 条件，取消质量分封顶，改为独立风险标记。此修订对本轮全部候选同等适用，不改写任何独立首轮报告，不重跑评审，也不改变开发委托、产品契约或非公开 harness 边界。Codex CLI 与 Grok Build 均不具有校准或改写本轮规则的特权，仍与其他系统使用同一绝对量表。

后续发现规则漏洞时，登记为下一版 baseline 的改进；本轮只允许经用户确认、且对全部候选统一适用的展示规则修订。

## 人工介入、环境与效率

Agent 可以正常提问、提出取舍或请求产品决策。人工只回答需求事实、业务取舍、明确授权和环境事实，不提供代码、调试步骤、架构方案或评分线索。影响共同产品事实的回答必须版本化并同步给所有尚未完成的运行；仅影响某一 Agent 上下文的问题单独记录。

人工不得直接修改候选结果、运行候选代码或替其修复环境。环境故障只能按同等方式恢复并记录。人工提问、回答、介入时长和原因属于效率元数据，不直接加减质量分。

不同候选的提示词一、二可在各自隔离 worktree 中受控并行，但只处理文档治理与设计；不得查看、读取、比较或使用其他并行工作树、分支、结果或运行记录，也不得提前进入提示词三。提示词三、所有 Compose、数据库、浏览器和端到端验证，以及最终复现必须串行执行。每个运行使用同一宿主机和基础环境；完成运行时工作后停止其 Compose 实例，再开始下一次运行。若发生资源竞争，最终运行效果与性能证据必须串行复测。

效率记录至少包含实际时长、token、成本、人工介入、环境异常和文档阶段的并行时间窗。共用外部 skill 基线与 Agent 实际使用的 skill 另写入 skill 记录；二者都不参与质量 100 分，可在结果汇总中单独比较。

```text
      codex-followup.md
```

`shared-external-skills.json` 冻结所有候选共用的外部 skill 清单与哈希。`skills.json` 记录本次实际使用的外部 skill 和已知内建 skill；未报告的内建 skill 必须标为“未报告”。`codex-review.md` 与 `grok-review.md` 只保存各自互盲的首轮审查，`review-summary.md` 在两份报告冻结后计算分数并确认风险标记。`scorecard.md` 记录各项得分、部分通过理由、风险标记、质量分和单列过程记录。`remediation/` 只在首轮后发生反馈修复时创建，不改变首轮归档。`efficiency.json` 记录效率元数据。原始日志和截图作为证据附件，不复制到产品仓库。

## 延后决策

- 自动化批量调度、公共排行榜和 Web 结果展示不属于本轮范围。
- 具体非公开 harness 的实现、命令和测试数据在首个正式候选的最终复现前冻结；此后所有候选使用同一版本。本文只固定其边界和归属。
- 新系统加入本轮前必须使用已冻结的 baseline、开发委托、评分规范、harness 和环境版本。
