# DecisionHarbor v0.1.0 评审与评分规范

## 范围与目标

本文定义 DecisionHarbor `baseline-v0.1.0` 首轮开发任务的运行、复现、评审和评分规则。它评价完整的 AI 开发 Agent 系统在同一产品起点、同一开发委托和同一运行环境中，能否交付安全、可运行、可维护的产品基座。

本轮质量分为 100 分。时间、token、成本与人工介入另行记录，用于效率比较，不进入质量总分。产品仓库不得保存本文、评分规则、隐藏用例或结果比较材料。

当前计划记录的系统标签如下；标签只用于归档，不影响评分：

- Codex CLI：`gpt-5.6-sol-xhigh`
- Grok Build：`grok-4.5-high`
- Kimi Code：`kimi-k3-thinking`
- ZCode：`glm-5.2-high`
- Qwen Code：`qwen-3.8-max`（未来可加入）

## 固定输入与不变量

每次运行必须记录并冻结：

- DecisionHarbor 产品仓库远端、`baseline-v0.1.0` tag 和精确 commit；
- 开发委托版本、固定销售数据集版本和数据契约哈希；
- 宿主机、Docker、Node.js、Python、PostgreSQL 和浏览器版本；
- 分支名、结果 commit、开始/结束时间、token、成本和人工介入记录。
- 共用外部 skill 基线的目录、清单与 `SKILL.md` 哈希，以及本次实际使用的外部 skill；Agent 内建 skill 单独如实记录，不猜测或补齐。

每个系统从相同 baseline 创建独立分支和 worktree。运行中不得读取、比较或使用其他结果 worktree、分支、提交、运行记录、评审材料或已完成答案。分支名可以包含 Agent 与模型名称；评审时不得因名称、模型、成本、耗时或既往印象改变任何评分子项。

Agent 的原生工具、搜索、浏览和工作方式属于被评系统的一部分，不作限制。允许正常访问依赖仓库、镜像仓库、操作系统包源、官方技术文档与正常搜索；不得为某一系统额外提供私有依赖、镜像缓存、账号或人工检索结果。

## 关键决策与取舍

| 决策 | 结论 | 理由与放弃的方案 |
| --- | --- | --- |
| Codex 的角色 | Codex CLI 用于统一复核，不是满分参照或规则校准特权。 | 相对 Codex 给分会把特定实现风格误当产品标准；所有系统改用同一绝对量表。 |
| 工具能力 | 保留每个 Agent 的原生工具与搜索能力。 | 本项目评价完整 Agent 系统；强行抹平工具能力会改变被评对象。 |
| 技能环境 | 所有候选使用同一份共用外部 skill 清单；内建 skill 不做抹平，但必须如实记录。 | 外部技能差异会形成不可追溯的额外输入；内建能力属于 Agent 系统本身，不能假定各系统相同。 |
| 质量与效率 | 质量 100 分独立，效率单独记录。 | 计费、token 与原生工具差异过大，不应掩盖产品交付质量。 |
| 复现与评审 | 提示词一、二可受控并行；实现、运行时验证和复现串行，统一环境，Codex 只读复核。 | 文档阶段不占用 Compose 运行资源；实现和复现阶段的并发资源竞争会污染证据，评审修改结果会破坏可追溯性。 |
| 验收材料 | 公开契约配合同一份非公开边界 harness。 | 只公开用例会弱化安全边界，完全隐藏又无法让开发目标可理解。 |

## 质量分与评分档位

质量原始分按下表计算。除人工裁定项外，每个子项使用三档：未通过为 `0`，部分通过为该子项的 `50%`，完全通过为满分。非公开 harness、命令输出、HTTP 响应、浏览器证据和代码审查是判断依据；Agent 自述不构成通过证据。原始总分可以保留 `0.5` 分。

| 维度 | 分值 | 子项 |
| --- | ---: | --- |
| 功能与外部契约 | 25 | 查询运行 API 生命周期 8；允许查询结果正确性 7；拒绝与执行失败语义 5；最小查询工作台 5 |
| SQL 治理与数据正确性 | 20 | AST 只读语义与单语句约束 6；授权对象与 schema 范围 4；数据库身份与双库隔离 4；执行资源限制 3；固定数据契约与业务口径 3 |
| 可运行性与可靠性 | 20 | 干净环境启动与就绪 6；迁移与固定数据初始化 6；并行实例隔离 5；重启与故障可见性 3 |
| 测试与验证证据 | 15 | 统一测试入口与可靠断言 3；SQL 策略单元测试 5；双数据库集成测试 4；浏览器主链测试 3 |
| 代码质量与可维护性 | 10 | 模块边界与职责分离 3；配置、错误处理与资源清理 3；类型、命名、重复控制与可测试性 2；依赖、变更范围与维护负担 2 |
| 产品文档与交付清晰度 | 5 | 治理、索引与阅读入口 1；设计完整性与可追溯性 2；计划、运行/测试说明与实现一致性 2 |
| 自发前端视觉质量 | 5 | 由人工在固定观察场景下综合评分 |

### 功能与外部契约

- 查询运行 API 生命周期：`POST /api/v1/query-runs` 创建查询记录，`GET /api/v1/query-runs/{id}` 可读取状态与审计事实。
- 允许查询结果正确性：针对固定数据集的筛选、聚合、连接或 CTE 查询返回正确列、行、行数和耗时。
- 拒绝与执行失败语义：非法输入具有稳定状态、错误码、可读说明和记录标识，不伪装为成功。
- 最小查询工作台：可输入与提交 SQL，显示执行中状态、成功结果、拒绝或失败信息。

### SQL 治理与数据正确性

- AST 只读语义与单语句约束：允许 `SELECT` 与 `WITH ... SELECT`；拒绝多语句、DML、DDL、数据修改型 CTE 与 `SELECT INTO`。策略必须基于 AST，不能退化为字符串黑名单。
- 授权对象与 schema 范围：只允许访问 `analytics` 中的五张业务表，拒绝系统目录、未授权对象与绕过限定的引用。
- 数据库身份与双库隔离：用户 SQL 必须由独立分析只读身份执行，不能读取或写入 `platform`。
- 执行资源限制：语句超时和结果行数上限真实生效。
- 固定数据契约与业务口径：五表、关联、数据、订单状态、销售额、成本和毛利计算符合契约。

### 可运行性与可靠性

- 干净环境启动与就绪：一条受支持命令构建并启动 Web、API 和 PostgreSQL；`/health` 与数据库、迁移就绪后的 `/ready` 成立。
- 迁移与固定数据初始化：两个逻辑数据库、身份、迁移和固定数据正确建立；重复执行不破坏或重复数据。
- 并行实例隔离：Compose 项目名和宿主端口可配置，不使用固定容器名、全局网络、全局卷或共享绑定目录；两个实例可同时存在。
- 重启与故障可见性：重启后服务可恢复；依赖未就绪时 `/ready` 准确失败。

### 测试与验证证据

- 统一测试入口与可靠断言：存在可执行的统一测试命令；失败产生非零退出，不依赖人工查看日志判断结果。
- SQL 策略单元测试：覆盖允许查询、DML/DDL、多语句、修改型 CTE、未授权对象和边界语法。
- 双数据库集成测试：证明迁移、seed、平台与分析库隔离、只读身份和实际查询执行。
- 浏览器主链测试：覆盖提交 SQL、执行状态、成功结果及至少一种拒绝或失败展示。

### 代码、文档与视觉

代码质量由独立 Codex 审查对话按表中 4 个子项评分。它必须引用具体代码或运行证据；个人风格不是扣分理由，只有会提高缺陷、扩展成本、运行风险或违反既有设计的具体问题才能扣分。Codex 的结果同样适用此规则；人工可纠正明显误判并记录理由。

文档项由 Codex 按表中 3 个子项给出结构化建议分和引用证据。人工根据实际内容表达与交付观感独立给出最终 `0–5` 分；若与 Codex 建议不同，记录简短理由。只评价产品内生文档，不要求面向评审的额外报告。

视觉项由人工独立给出 `0–5` 整数分。在同一桌面视口观察空态、输入 SQL、执行中、成功结果和拒绝或失败状态，综合评价信息层级、布局与密度、状态反馈、表格可读性、视觉一致性和细节完成度。它不奖励营销页、插画或超出需求的复杂交互，也不因功能分数低而额外扣分。

## 关键失败封顶

先计算原始质量分，再应用以下封顶；若多个条件同时命中，使用最低上限。

| 级别 | 条件 | 总分上限 |
| --- | --- | ---: |
| P0 安全失败 | 用户 SQL 能写入数据、访问系统或未授权对象、通过平台写入身份执行，或绕过 AST 治理 | 39 |
| P1 基座失败 | 无法在规定环境启动，或 `/health`、`/ready`、迁移、固定数据 seed 中任一核心链路不成立 | 59 |
| P2 核心闭环缺失 | 不能同时证明一条允许查询和一条拒绝查询，或最小查询工作台不可用 | 69 |

## 验收证据与评审流程

验收分为公开层和非公开层。公开层是产品背景已承诺的 API、数据契约、启动和测试要求。非公开层是同一份版本化 harness，覆盖 SQL 绕过、schema 或系统对象访问、真实只读权限、超时与行数限制、重复 seed、并行 Compose 和 API 边界。非公开用例只验证既定评分子项，不引入新需求；它只存在于 AgentShip 或外部评测环境，不进入产品仓库。

每个结果按以下顺序评审：

1. 冻结结果 commit、提示词版本、环境版本和运行元数据。
2. 在独立 review worktree 从头复现启动、迁移、seed、测试、健康检查、允许/拒绝 SQL 和浏览器主链，并保存命令和输出。
3. 从 AgentShip 当前工作区启动只读 Codex 审查对话。它可以查看结果、运行复现命令、检查代码与截图，但不得修改产品结果；它输出代码质量分、文档建议分、运行问题清单及证据。
4. 人工给出视觉项和文档最终分，并处理 Codex 的明显误判。
5. 记录各项得分和部分通过理由，应用封顶并形成最终分。

缺少必要环境导致无法执行的检查标为“未验证”，不得按通过计分。若有证据证明是评测环境故障，可在环境恢复后以同等条件复跑。

## 规则冻结

本次修订只澄清调度边界与并行工作树隔离，不改变背景资料、产品契约、评分分值或封顶条件。自本次修订起，`baseline-v0.1.0`、开发委托、评分细则、非公开 harness 边界和环境版本冻结。Grok Build 是首个正式候选；Codex CLI 不具有校准或改写本轮规则的特权，仍与其他系统使用同一绝对量表和封顶规则。

后续发现规则漏洞时，登记为下一版 baseline 的改进，不追溯修改本轮成绩。

## 人工介入、环境与效率

Agent 可以正常提问、提出取舍或请求产品决策。人工只回答需求事实、业务取舍、明确授权和环境事实，不提供代码、调试步骤、架构方案或评分线索。影响共同产品事实的回答必须版本化并同步给所有尚未完成的运行；仅影响某一 Agent 上下文的问题单独记录。

人工不得直接修改候选结果、运行候选代码或替其修复环境。环境故障只能按同等方式恢复并记录。人工提问、回答、介入时长和原因属于效率元数据，不直接加减质量分。

不同候选的提示词一、二可在各自隔离 worktree 中受控并行，但只处理文档治理与设计；不得查看、读取、比较或使用其他并行工作树、分支、结果或运行记录，也不得提前进入提示词三。提示词三、所有 Compose、数据库、浏览器和端到端验证，以及最终复现必须串行执行。每个运行使用同一宿主机和基础环境；完成运行时工作后停止其 Compose 实例，再开始下一次运行。若发生资源竞争，最终运行效果与性能证据必须串行复测。

效率记录至少包含实际时长、token、成本、人工介入、环境异常和文档阶段的并行时间窗。共用外部 skill 基线与 Agent 实际使用的 skill 另写入 skill 记录；二者都不参与质量 100 分，可在结果汇总中单独比较。

## 归档结构

每次运行在 AgentShip 中保存独立记录目录：

```text
baselines/DecisionHarbor/baseline-v0.1.0/
  shared-external-skills.json
  runs/<agent>-<model>/
    metadata.json
    skills.json
    intervention-log.md
    reproduction.md
    codex-review.md
    scorecard.md
    efficiency.json
    screenshots/
```

`shared-external-skills.json` 冻结所有候选共用的外部 skill 清单与哈希。`skills.json` 记录本次实际使用的外部 skill 和已知内建 skill；未报告的内建 skill 必须标为“未报告”。`scorecard.md` 记录各项得分、部分通过理由、封顶结论和最终质量分。`efficiency.json` 记录效率元数据。原始日志和截图作为证据附件，不复制到产品仓库。

## 延后决策

- 自动化批量调度、公共排行榜和 Web 结果展示不属于本轮范围。
- 具体非公开 harness 的实现、命令和测试数据在首个正式候选的最终复现前冻结；此后所有候选使用同一版本。本文只固定其边界和归属。
- 新系统加入本轮前必须使用已冻结的 baseline、开发委托、评分规范、harness 和环境版本。
