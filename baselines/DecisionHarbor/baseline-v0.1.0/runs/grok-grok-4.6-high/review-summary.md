## 风险标记确认

| 标记 | 汇总判断 | 依据 |
| --- | --- | --- |
| P0 安全失败 | 确认 | Codex 报告通过 API 复现 `SELECT CAST('pg_catalog.pg_class' AS regclass)` 成功并返回 `pg_class`；Grok 也复现同类 `regclass` / `::regclass` 语句会返回系统或未授权对象名。后者认为该路径不能读取目录行而不构成 P0，但评分规范将用户 SQL 对系统或未授权对象的访问及 AST 治理绕过列为 P0，故按可复核证据确认。 |
| P1 基座失败 | 未触发 | 两份报告均取得受支持启动、初始 `/health` 与 `/ready`、迁移、固定数据 seed 和恢复的成功证据。停止 PostgreSQL 后 `/ready` 仍返回 200 且查询端点变为无结构 500 是已计入技术分的可靠性缺陷；在当前规则展示中，它不改变已成立的启动与初始化核心链路结论。Codex 报告中的 P1 判断保持原样。 |
| P2 核心闭环缺失 | 未触发 | 两份报告均记录允许 SQL、拒绝 SQL 和浏览器工作台主链的新鲜运行证据。 |

P0 表示首轮不具备安全上线资格，但不改变技术平均分或未来质量分的算术公式。`/ready` 的运行期误报仍应在任何合入或发布前修复。
