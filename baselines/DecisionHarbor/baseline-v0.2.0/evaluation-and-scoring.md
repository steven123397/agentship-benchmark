# DecisionHarbor v0.2.0 评测与评分规范

## 评测对象

本轮评价完整 Agent 系统能否从 DecisionHarbor `baseline-v0.2.0`（`9355032ecadd6d3c940d7977fe381f9f8a93b1ab`）出发，消费仓库内 spec 和长期决策，通过本地 tickets 驱动多个独立实现会话，最终交付可恢复的异步查询生命周期。

所有候选使用相同冻结 baseline、[`development-brief.md`](development-brief.md)、[`shared-external-skills.json`](shared-external-skills.json) 所记录的用户级外部 skill 环境、运行环境、隐藏验证和评分尺度。Agent 或 Harness 自带的 skills 属于其自身能力，不纳入共同外部 skill 清单，也不因名称或数量获得额外分数。产品仓库不得保存本文、评分线索、隐藏用例或候选比较材料。

## 分数构成

质量分为 100 分，由两名互盲审查者分别评分后取算术平均：

| 维度 | 分值 | 评价对象 |
| --- | ---: | --- |
| 规格消费 | 10 | Agent 是否准确识别、覆盖并持续遵守 spec、CONTEXT 和 ADR 中的产品合同 |
| Ticket 拆分与演进 | 10 | 最终 tickets 是否形成可执行的纵向切片，以及实现期间能否根据新证据正确调整 |
| 实现质量 | 70 | 产品行为、安全、恢复、运行、测试和代码质量是否成立 |
| Skill 工作流证据 | 10 | `/to-tickets` 与 `/implement` 所要求的阶段、TDD、review 和 tracker 闭环是否有可信证据 |

两名审查者的总分均为 `0–100`，最终质量分可保留 `0.5` 分。时间、token、成本、人工介入、环境异常和风险标记单独展示，不直接改写质量分。本轮不设置独立文档分或视觉分；产品文档、Web 状态反馈、响应式与可访问性分别在相关实现子项中评价。

## 1. 规格消费（10 分）

| 子项 | 分值 | 满分条件 |
| --- | ---: | --- |
| 合同覆盖 | 4 | 最终 tickets、实现与测试覆盖 spec 的外部 API、状态、恢复、取消、结果、配置和回归合同，没有无主需求或静默遗漏 |
| 约束与优先级 | 3 | 正确保留 CONTEXT/ADR 和 v0.1 不可退化边界；没有用局部实现便利覆盖安全、数据或生命周期不变量 |
| 歧义与实现自由 | 2 | 只对真实产品歧义请求决策；普通实现选择自主完成，且没有把 spec 未规定的偏好误写成产品合同 |
| 端到端追踪 | 1 | 能从 spec 条目追到 ticket、实现提交、测试和 Resolution，关键合同的证据链完整 |

规格消费不根据 Agent 的思维过程或自述评分。评分依据是最终 tickets、问题与回答记录、代码、测试、提交历史和可复现行为。一个规格遗漏如果同时造成产品缺陷，可以分别影响本维度和实现质量：前者评价理解与追踪，后者评价实际交付结果，不视为重复扣分。

## 2. Ticket 拆分与演进（10 分）

| 子项 | 分值 | 满分条件 |
| --- | ---: | --- |
| 纵向切片与覆盖 | 3 | 每张 ticket 交付可验证的端到端增量；全部 tickets 合起来覆盖 spec，且没有大面积重复或长期只搭骨架的横向切片 |
| 依赖与 frontier | 2 | `Blocked by` 反映真实 blocking edges；frontier 可执行，不依赖隐含顺序或循环依赖 |
| 验收条件 | 2 | 每张 ticket 的验收条件具体、外部可观察并能由测试或运行证据判定 |
| 会话规模 | 1 | Ticket 能在一个新上下文中完成，范围与提交边界清楚，不靠顺带实现其他 ticket 才能成立 |
| 适应性修正 | 2 | 实现发现新依赖、错误假设或切片问题时，及时且可追踪地调整 tickets、依赖和验收，不丢失已确认合同 |

规划提交用于还原演进过程，不作为不可修改的计分快照。初始拆分质量较低，但候选在实现过程中识别问题并把最终 tickets 修正到可靠状态，可以获得完整 Ticket 分和适应性分。实现结束后才进行的装饰性回填，如果没有影响实际会话边界、依赖选择或验收过程，不构成适应性证据。

## 3. 实现质量（70 分）

### 异步功能与外部合同（20 分）

- 提交、运行读取、结果读取和历史分页：5 分。
- 状态迁移、不可逆终态与稳定错误合同：4 分。
- 排队/运行取消、幂等取消和竞态结果：4 分。
- 失败/取消重试、`retry_of` 和幂等重放：3 分。
- 结果快照、类型表示、截断、过期和清理：2 分。
- Web 轮询、状态反馈、桌面/窄视口与键盘主流程：2 分。

### 并发、一致性与恢复（18 分）

- 两个 Worker 与数据库协调的全局有效所有权上限：4 分。
- 租约、心跳、失租接管和运行状态连续性：4 分。
- generation fencing 与单一可发布所有者：4 分。
- `cancelling` 收敛、取消后不再尝试和迟到结果丢弃：3 分。
- 自动尝试分类、3 次上限、Worker 崩溃与重启恢复：3 分。

### SQL 治理与数据正确性（10 分）

- AST 默认拒绝、对象/函数/类型范围和绕过回归：4 分。
- analytics 只读身份、API/Worker/就绪凭据边界：2 分。
- 固定数据契约、金额精度和稳定结果类型：2 分。
- 超时、有界提取、错误脱敏和审计事实：2 分。

### 可运行性与资源可靠性（8 分）

- 干净 Compose 构建、迁移、seed、Web/API/Worker 健康与就绪：3 分。
- 重复启动、fail-closed seed、结果清理和失败路径资源收敛：2 分。
- 多工作树项目名、端口、网络和数据卷隔离：2 分。
- 非法配置启动失败和统一测试入口非零失败语义：1 分。

### 测试与验证（8 分）

- 公开 HTTP 与浏览器端到端主链：2 分。
- 真实 PostgreSQL 双 Worker、租约、fencing 和取消竞态：3 分。
- 结果字节/行数、幂等、重试、过期和清理边界：2 分。
- v0.1 安全、数据与运行回归：1 分。

### 代码与产品文档质量（6 分）

- API、Worker、状态、持久化与结果边界清晰，核心模块具有足够深度：2 分。
- 条件更新、事务、连接、游标和进程资源管理易于推理：2 分。
- 类型、命名、错误模型和配置一致，没有与任务无关的复杂化：1 分。
- CONTEXT、ADR、README 和 ticket Resolution 与实际实现同步：1 分。

## 4. Skill 工作流证据（10 分）

| 子项 | 分值 | 满分条件 |
| --- | ---: | --- |
| 阶段与上下文边界 | 2 | 先完成 `/to-tickets` 与规划提交，再按 frontier 为每张 ticket 开启独立 `/implement` 会话；一次会话不顺带下一张 |
| Tracker 闭环 | 2 | ticket 状态、依赖、验收勾选、Resolution、验证和提交 SHA 与实际历史一致 |
| TDD 证据 | 2 | 能从会话记录、测试变更或工具输出确认关键行为经历失败测试、实现和回归，而非只在最后补测试 |
| Review 与修复 | 2 | 每张 ticket 的 Standards/Spec review 有可核验结论；发现被修复、复核或如实保留，不把未处理发现描述为通过 |
| 证据真实性 | 2 | skill 使用、命令、测试、未验证项和人工介入均有来源；没有根据模板补写未发生的过程 |

不按调用的 skill 数量、名称或输出篇幅加分。可选 skill 只有在改变了可观察工作质量时才作为背景证据；`skills.json` 或 Agent 自述不能单独证明 TDD、review 或验证已经发生。不同 Agent 的内建能力不做抹平，但所有候选必须面对相同的外部 skill 基线和固定提示词。

## 运行记录合同

候选完成后，协调方根据已经发生且可核对的事实创建运行归档；启动候选时不创建占位目录或空记录。JSON 文件必须分别通过本目录中的同名 schema：

- `metadata.json`：候选、Harness、baseline、规划与结果 commit、阶段、冻结状态、skill 环境和 Codex/Cursor 首轮评分索引。
- `efficiency.json`：规划会话和逐 ticket 会话中可观测的时间、token 与成本；不可观测字段使用 `null`，不估算。
- `skills.json`：实际使用且有证据的用户级全局 skills，以及 Harness 自带 skills；名称和数量本身不评分。
- `workflow.json`：规划与逐 ticket 执行顺序、提交、tracker、TDD 和 review 的证据索引。

`reproduction.md`、`intervention-log.md`、两份原始评审报告、`review-summary.md` 和 `scorecard.md` 继续承担叙述性证据与汇总职责。相同事实只写入职责对应的一个文件，其他记录使用路径引用。

### `workflow.json` 证据合同

每个候选归档必须创建 `runs/<candidate-id>/workflow.json`，并符合 [`workflow.schema.json`](workflow.schema.json)。该文件由协调方根据可核对事实维护，是工作流证据索引，不是候选自述或完整开发日志。

- `planning` 记录 `/to-tickets` 会话引用、baseline 起点、规划提交和证据来源。
- `tickets` 按实际执行顺序记录 ticket 路径、独立会话引用、起止提交、tracker 状态、Resolution、TDD 和 review 证据。
- `sessionRef` 在平台无法提供稳定引用时使用 `null`，但不能据此推断会话边界已通过；应由 Git、ticket 或协调方记录补充证据。
- `resultCommit`、`resolutionRef` 或某类证据无法确认时使用 `null`、空数组或 `unverified`，不得编造占位引用。
- `workflow.json` 不记录 token、成本、耗时和普通环境异常，这些属于 `efficiency.json`；不记录非标准人工介入正文，这些属于 `intervention-log.md`；不复制复现命令输出，这些属于 `reproduction.md` 或独立日志附件。

评审者先验证 schema、候选身份、提交链和 ticket 顺序，再用其中的引用读取原始证据。`workflow.json` 中一个字段的存在只证明协调方记录了该声明；最终得分仍取决于引用是否存在、内容是否匹配以及更高优先级证据是否支持。

## 评分档位与证据规则

每个列明分值的子项按 `0% / 50% / 100%` 三档评分：

- `100%`：合同完整成立，并有可复现证据。
- `50%`：核心路径成立，但存在明确边界缺口、证据不足或只覆盖单实例/理想路径。
- `0%`：缺失、与合同冲突、无法运行，或只有未经核验的自述。

证据优先级从高到低为：独立复现与隐藏验证、候选代码和 Git 历史、产品内 tickets/测试/Resolution、可核对的会话或 Harness 记录、Agent 完成报告。高优先级证据冲突时，以可重复观察的实际行为为准。评审不得要求私有方法名、固定表结构、特定领取 SQL、锁、线程模型或 spec 未规定的实现细节。

## 风险标记

- **P0 安全失败**：异步路径绕过 AST、对象范围或只读身份，能够访问未授权对象或写入数据。
- **P1 基座失败**：干净环境、迁移、seed、就绪、Worker 启动或两个副本中的核心基座无法成立。
- **P2 生命周期缺失**：不能证明合法查询从排队到终态，或取消、接管、fencing、结果读取中的任一核心闭环不可用。

风险标记不额外扣分、不封顶，但根因必须在对应实现子项中反映。过程证据不足直接影响规格、Ticket 或 Skill 分，不伪装成产品安全风险。

## 隐藏验证边界

隐藏 Harness artifact 由可移植的公开 HTTP runner 和统一故障场景协议组成，只验证冻结 spec 已声明的行为：幂等作用域与冲突、状态转换、历史游标、两个 Worker 的有效所有权、租约接管、旧 generation、取消收敛与终态竞态、自动尝试分类和上限、结果编码/行数/字节/过期、幂等清理、重试关系、v0.1 SQL/权限/seed 回归和 Compose 隔离。需要故障注入或精确边界构造的场景可以使用候选已有的运行与真实数据库测试接缝，但通过条件和证据等级对所有候选相同。

隐藏用例不得引入产品仓库未声明的新需求，也不得把某个候选的内部实现当作标准答案。隐藏 Harness 必须在首个正式候选开始开发前完成并生成符合 [`harness-manifest.schema.json`](harness-manifest.schema.json) 的实际 manifest；此后所有候选使用同一 artifact、入口和环境合同。实际 manifest 属于协调方与审查者证据，不向候选提供。

## 评审流程

1. 冻结候选结果 commit、规划 commit、提示词版本、skill 环境快照、环境版本和可获得的会话证据，并生成通过 schema 校验的 `metadata.json`、`efficiency.json`、`skills.json` 与 `workflow.json`。
2. 独立复现固定数据校验、统一测试入口、Compose 启动、公开 API、双 Worker 故障场景、安全探针和浏览器主链。
3. Codex 与 Cursor 分别取得同一候选证据包，按 [`review-prompts.md`](review-prompts.md) 独立完成 100 分评分和风险标记；汇总前不得读取对方报告。
4. 两份报告冻结后计算算术平均，记录分歧、环境异常、未验证项和人工事实纠正。人工不得以偏好改写评分，只能凭证据修正事实或计算错误并记录理由。
5. 首轮结果冻结后，反馈修复只记录修复效果，不覆盖首轮 commit、评分和风险标记。
